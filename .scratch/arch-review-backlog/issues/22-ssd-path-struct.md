# 22: The scan options are an SSD path and a chunk length

Status: resolved

Blocked by: None

From the architecture review of 2026-11-16. Line numbers are those of commit
`7807d31b`.

**Files:** `src/mamba3/ssd_path.rs:30-155`, `src/mamba2/ssd/ssd_path.rs:19-30`,
`src/family/mod.rs:82-112`, `src/family/adapters.rs` (the two `reset_align`).

**Problem:** `Mamba2SsdPath` and `Mamba3SsdPath` each have three variants with the
same payload: `Minimal(Option<usize>)`, `Serial(Option<usize>)` and
`SerialRecalculated(Option<usize>)`. That is a product written as a sum. So
`chunk_len()` matches all three variants to read one field, and a test passes a
variant as `fn(Option<usize>) -> Mamba3SsdPath` to set the chunk length
(`src/family/tests/block_contract.rs`, `m3_path`).

**Direction:** A struct with two fields: the kind (`Minimal`, `Serial`,
`SerialRecalculated`) and the chunk length. Ticket 18 then adds the pathway as a third
field of the Mamba-3 struct.

**Cost:** A break of the public API at each site that names a variant: the examples
(`--ssd-path`), the tests and the benches. The change is mechanical. Do it with
ticket 18, or directly before it, so that the callers change one time.

## Agent brief

**Category:** enhancement

**Summary:** One enum `SsdPath` gives the SSD path of Mamba-2 and Mamba-3. The scan
options of each family are a struct with two fields: the SSD path and the chunk length.

**Current behaviour:**

- `Mamba2SsdPath` and `Mamba3SsdPath` are enums with three variants. Each variant holds
  the same optional chunk length. The family enum `MambaSsdPath` holds one of them, or
  nothing for Mamba-1.
- Each one is the `Block::Options` of its block. The `forward` calls of the blocks take
  it, and `reset_align` reads its variant.
- `run` of the input bundles `Mamba2SsdInput`, `Mamba3SingleSsdInput` and
  `Mamba3DoubleSsdInput` takes the path type, but it reads only the variant.
- The examples tiny-stories and hnet-stories parse `--ssd-path <p>[:<l>]` into a
  `Mamba3SsdPath`. hnet-stories also has `--main-ssd-path`.

**Desired behaviour:**

- Each call computes the same values as before. Only the types, the names, the flags
  and the docs change.
- The types and the names are those of **Key interfaces**.

**Key interfaces:**

- **`crate::ssd_path::SsdPath`**, a new enum:
  - The variants are `Minimal`, `Serial` and `SerialRecalculated`. The default is
    `SerialRecalculated`.
  - It derives `Debug, Clone, Copy, PartialEq, Eq, Default, serde::Serialize,
    serde::Deserialize`.
  - It exists when `mamba2` or `mamba3` is on, as `standard_ssd` does.
  - The doc of each variant joins the docs of the two old variants. It cites the
    functions of both families.
  - Each prelude that exports an old enum exports `SsdPath`.
- **`mamba2::scan_options::Mamba2ScanOptions`** and
  **`mamba3::scan_options::Mamba3ScanOptions`**, structs with
  `#[derive(Config, Debug)]`:
  - The field `pub ssd_path: SsdPath` is required. So the constructor is
    `new(ssd_path)`.
  - The field `pub chunk_len: Option<usize>` gets `with_chunk_len(Option<usize>)` from
    the derive. `None` gives the optimal chunk length of the block, as today.
  - A manual `impl Default` returns `Self::new(SsdPath::default())`.
  - `optimal_chunk_len` and `chunk_len_or_optimal` keep their signatures and their
    math.
  - `chunk_len()` and `default_optimal_from_block` go.
  - A call reads `Mamba3ScanOptions::new(SsdPath::Serial).with_chunk_len(Some(64))`.
  - The header of `mamba3::scan_options` has no sentence about `From` conversions.
  - The four tests of the chunk-length schedule go with the Mamba-3 struct.
- **`family::MambaScanOptions`**, the new name of `MambaSsdPath`:
  - It derives `Config` and `Debug`, as `MambaBlockConfig` does.
  - The variants are `Mamba1`, `Mamba2(Mamba2ScanOptions)` and
    `Mamba3(Mamba3ScanOptions)`. `mamba2_default()` and `mamba3_default()` stay.
  - If the derive does not compile on this enum, keep `#[derive(Debug, Clone)]`. Write
    the reason under `## Comments`.
- **`Block::Options`** of `Mamba2`, `Mamba3` and `MambaBlock` are these three types.
  Each `reset_align` compares `options.ssd_path == SsdPath::Minimal` and has no
  `match`.
- **`run`** of `Mamba2SsdInput`, `Mamba3SingleSsdInput` and `Mamba3DoubleSsdInput`
  takes `ssd_path: SsdPath` by value. `Mamba2SsdInput`, its `run` and its agreement
  tests stay in `mamba2::ssd::ssd_path`. The two Mamba-3 modules `…::ssd::ssd_path`
  keep their names.
- **Names:**
  - An identifier that holds a whole scan options value is `scan_options`, or it ends
    in `scan_options`. An identifier that holds only an `SsdPath` is `ssd_path`.
  - This rule covers the parameters of each `forward` and the fields of the example
    runs, for example `Run::ssd_path` and the `paths` pair of hnet-stories. It also
    covers the extractors of `MambaBlock` and the helper `m3_path` of the block
    contracts. That helper takes an `SsdPath`.
  - The panic of a wrong family says "the family of the scan options does not match
    the block". Its `should_panic(expected = …)` changes with it.
- **Flags of the examples:**
  - `--ssd-path <p>` takes `recalc` (the default), `serial` or `minimal`.
    `parse_ssd_path` returns `SsdPath`.
  - `--ssd-chunk-len <l>` sets the chunk length, in write positions. A value below 1
    is an error, as `:0` is today. With no flag, the shape of the block gives the
    chunk length.
  - In hnet-stories, `--main-ssd-path` and `--main-ssd-chunk-len` set the main stack.
    Each one defaults to the value of the stages.
  - The help strings, the README tables, `examples/README.md` and the docs of the
    fields describe the new flags.
- **Docs:**
  - The docs say "scan options" for the struct, and "SSD path" only for the enum.
  - The README links point to the new rustdoc pages.
  - The File Map has a line for `ssd_path.rs` under `src/`, and a line for
    `scan_options.rs` under `mamba2/` and under `mamba3/`.
  - `docs/agents/testing.md` gives the new path of the tests of the chunk-length
    schedule.
  - `info/mamba-3/architecture-deltas.md` uses the new constructor.
