## Agent brief

**Category:** enhancement

**Summary:** burn-mamba follows burn-stack ticket 13. The three `init_applications` go,
and each family init builds the block for one application. A table test of each
family checks the tensors that each untie choice names.

**Current behaviour:**

- `Mamba1Config`, `Mamba2Config` and `Mamba3Config` have
  `init_applications(n_applications, device)`. It tiles each untied parameter by hand
  with `untied::tile(param, axis, copies(…))`. `init(device)` calls it with 1.
- `Mamba1::untied_params`, `Mamba2::untied_params` and `Mamba3::untied_params` give the
  axis of each parameter again.
- The `BlockConfig` impls of the three configs and of `MambaBlockConfig` take a count
  of applications.
- The block contract finds a tensor that grows with the count and that
  `untied_params` does not name. burn-stack ticket 13 removes that check.

**Desired behaviour:**

- The init of each family calls no `untied::tile`. The layer tiles each parameter
  that `untied_params` names (burn-stack ticket 13).
- The copies of each untied parameter start from the same draw, as before.
- At a fixed seed, most settings start from the same values as before. These settings
  start from other values: a real layer with more than one application that unties
  Mamba-2 `InProjTail` or `Conv1d`, or Mamba-3 `InProjTail`. The cause is the lazy
  draw of Burn (see the **Triage notes** of burn-stack ticket 13). So
  `examples/mnist-class` starts from other values.
- A table test of each family fails when `untied_params` misses a tensor of an untie
  choice, names a wrong tensor or gives a wrong axis.

**Key interfaces:**

- **The pin**: both `rev` values of burn-stack in `Cargo.toml` are the pushed commit
  of burn-stack ticket 13 (burn-stack version 0.45.0). The `[patch]` is a comment.
- **`Mamba1Config`, `Mamba2Config` and `Mamba3Config`**:
  - `init_applications` goes. `init(device)` builds the block for one application.
    Each config check of the init stays, with its message.
  - The split of the `in_proj` tail stays in the init. With `InProjTail` untied,
    `in_proj_tail` has the width of one application.
  - The `copies` closures go.
- **`untied_params` of each family** does not change. It is the one list of the untied
  parameters and of their axes.
- **The `BlockConfig` impls** of the three configs and of `MambaBlockConfig`:
  `init_block(&self, device)` calls `init`.
- **The table tests**: three new tests in `src/family/tests/untied.rs`, one for each
  family.
  - Each test has one row for each untie choice. A row gives a config with the tensor
    of the choice, and the paths and the axes of its tensors.
  - The config of each row enables each optional tensor of its choice. Examples: the
    biases, the learnable initial state, `mimo_rank` 2, the output norm, a Kalman gain,
    `Tropical::MaxPlus`.
  - The test builds the block of each row with the one untie choice. It compares the
    paths and the axes of `untied_params` with the row.
  - An exhaustive `match` on the untie enum gives the rows. So a new untie choice does
    not compile without its row.
  - A failure collects one line for each wrong row, with the name of the untie choice.
  - The rows give what the code gives now:

  the exhaustive `match`. A list of the untie choices beside it gives the order of

  the list does not get the new choice automatically, so a new choice also goes into
  the list by hand.

  which is also its default.

  family, so the file compiles with each family alone.
- `mamba3_layout_follows_the_untie_list` tiles through a closure: the block of a
  config, then `untied::tile(block, &params, 3)` with the `untied_params` of that block.

### Review

> *This was generated by AI during implementation.*

`/code-review` ran on `git diff 8858292e`, with one Standards agent and then one Spec
agent. The reports are `tmp/review-t24-standards.md` and `tmp/review-t24-spec.md`.
The Spec agent found no wrong implementation and no scope creep.

Fixed:

- "row" had a second meaning: the glossary of burn-stack defines **Row** as one
  sequence of a batch. The table tests call a table entry a "case" (`fn case`, the
  docs and the two failure messages).
- The header sentence "So that contract does not see" read as "so that". It is
  "So the contract does not see".
- The doc of each `fn case` said "a config with each tensor of `part`, and these
  tensors". It says "a config that enables each tensor of `part`, and the path and
  the axis of each such tensor".
- The type `Tensors` holds paths and axes, so it is `PathAxes`. The closure parameter
  of `check_table` is `build`, because it builds a block.
- The doc of `check_table` treats `untied_params` as singular, as the rest of the
  file does.
- The Spec agent found one more setting whose start values change at a fixed seed:
  `examples/mnist-ae` unties Mamba-3 `InProjTail` over 2 real layers run as 4 virtual
  layers. The commit message names it with `examples/mnist-class`.

Not fixed:

- `param_paths` repeats the path visitor of `ParamShapes` in
  `src/family/tests/block.rs`. `ParamShapes` reads the shape of each parameter, so it
  draws each lazy parameter. The table tests need only the id. A shared visitor also
  changes `block.rs` beyond the `init_block` calls of this ticket.
- The three test bodies have the same shape. Each family has its own config type and
  its own `with_untied`, so a shared body needs a new trait for three lines.
- The list of the untie choices of each test is a second list beside the `match` (see
  **Implementation notes**). Rust gives no list of the variants of an enum without a
  macro or a new dependency. The block contracts have the same hand-written lists.
