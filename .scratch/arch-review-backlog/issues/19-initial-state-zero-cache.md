**Problem:** `init_state_hpr` goes through 3 input bundles to 9 scans. The 3 `Minimal`
scans add it to the initial state. The 6 serial scans panic ("not yet implemented").
So the default SSD path panics when `has_learnable_init_state` is on. Two more facts
break block contracts when the state is not zero:

- `step` does not read it (`src/mamba2/mamba2.rs:1086`), so the forward is not equal to
  the step unrolled.
- Each forward adds it to the state of its cache. So a forward in two windows adds it
  two times, and is not equal to one forward.

The block contracts leave `InitState` out for this reason. A grep found no test and no
example that sets the option.

**Direction (superseded at triage):** The zero cache holds `h₀`, broadcast over the rows. Each SSD path, both
pathways, `step` and each segment of a packed row with no origin then start from it.
A carried cache already holds its state, so no call adds `h₀` to it. The input bundles
and the scans lose the field, and the 6 panics go.

**This changes a documented behaviour (superseded at triage).** The glossary says that each forward adds it
to the state of its cache. The official code does the same with `init_states`
(`../py/state-spaces/mamba/`). At the init (`h₀ = 0`), the values do not change. The
user decides this at triage. The glossary entry changes with the code.

**Also in burn-stack (superseded at triage):** `zero_caches_for` (`../burn-stack/src/modules/layers.rs:799`)
builds each slot from application 0. An untied `InitState` needs the application of
each slot. Split this ticket by repo at triage.

**Not checked:** The gradient of `h₀` through `zero_cache` under a gradient horizon
and in a captured step.

## Triage notes

> *This was generated by AI during triage.*

**Checks against the code** (burn-mamba at `bcfbea63`, burn-stack at `012a430`). No
build ran.

- The problem holds. `init_state_hpr` goes into the three SSD input bundles
  (`Mamba2SsdInput`, `Mamba3DoubleSsdInput`, `Mamba3SingleSsdInput`), and from there to
  9 scans. The 3 `Minimal` scans add it to the start state of the call. The 3 `Serial`
  and the 3 `SerialRecalculated` scans assert that it is `None`. `SerialRecalculated` is
  the default SSD path.
- `step` starts from the zero cache, and it does not read the field. A forward from a
  cache that a call returned adds the field again.
- A packed call with the option on panics on every path. `Minimal` takes no resets
  (`packed_minimal_panics`), and the serial paths refuse the field. The review did not
  see this.
- The official code holds `init_states` as a module parameter (`mamba2_simple.py`).
  That module has no inference cache, so each forward starts from `init_states`. With
  `seq_idx`, the state passing sets the state to zero at a new sequence
  (`ssd_state_passing.py`). So only the first sequence of a packed row starts from
  `init_states`.
- The family API already takes a start state from the caller:
  `forward_packed(x, cache, origin, …)`. Each row starts from `cache`, and each segment
  starts from `origin`. Autodiff is a property of each tensor, so a trainable tensor in
  either one gets a gradient:
  - `src/packing/tests.rs` makes the origin a leaf, and it checks the gradient of the
    origin on Mamba-2 and Mamba-3.
  - The form-agreement tests compare `d_init_state` on each SSD path.
  - The custom backward of `SerialRecalculated` returns `d_initial_state` and
    `d_origin_bhpr`.
- The forward/step parity tests of each family start from a random cache. So they
  cover a start state in a cache.
- The `Block` adapters of Mamba-2 and Mamba-3 call `forward_packed` with
  `origin: None`. `Block::block_forward_packed` of burn-stack takes no origin. So in a
  container, each segment starts from the zero cache.
- No zero cache reads a parameter. The zero-state builders of Mamba-3 read only the
  config and the shapes.
- No `.out-of-scope/` directory exists in either repo.

**Decisions of the maintainer** (a grilling session):

1. The meaning of `h₀`: it is the start state of a fresh sequence.
   - A packed segment acts as one batch row in serial form. So each segment starts from
     the origin.
   - No call adds `h₀` to a cache that a call returned. That cache already holds what
     `h₀` became.
   - Every SSD path gives `h₀` the same meaning.
   - For packed rows, this departs from the official code. An ADR records this.
2. Where `h₀` lives: the caller gives it in a cache. The block holds no parameter for
   it, and the config has no option for it. The tensor decides whether `h₀` trains. A
   call with no cache starts from the zero cache.
3. This ticket **moves** the capability. It does not delete it.
4. Each Mamba-2 and Mamba-3 block gets a helper that builds a cache from a state:
   `cache_with_state`. The name avoids the glossary term **Start state**, which is the
   state of a segment at its reset.
5. burn-stack ticket 18 adds the origin to `Block::block_forward_packed` and to the
   packed forward of the containers. It blocks this ticket.
6. The zero cache stays all zeros, and it keeps its name. The rename to `fresh_cache`
   is not necessary. The change of `zero_caches_for` (decision 4 of burn-stack ticket
   12) is not necessary.
7. Each block contract adds noise to the weights first: burn-stack ticket 19. It waits
   for this ticket, because it runs the block contracts of burn-mamba.

## Agent brief

**Category:** enhancement

**Summary:** The learnable initial state `h₀` of Mamba-2 and Mamba-3 moves from a
parameter of the block to a cache that the caller gives. Every SSD path then takes it,
at the start of each row and at the start of each segment.

**Read this before you start: this ticket moves a capability. It does not delete it.**

- Most of the diff deletes code. **Desired behaviour** gives each item that goes.
- The capability stays, and it grows. After this ticket, a caller can train a start
  state on every SSD path, in `forward`, in `step` and in a packed call. Before this
  ticket, only `Minimal` read it, and only in a forward with no packing.
- The capability moves to the caller. The caller holds `h₀`, for example as a `Param`
  of its own module. It builds a cache from `h₀` with `cache_with_state`. It gives that
  cache as `cache`, as `origin`, or as both.
- An implementation that deletes `init_state_hpr` but adds no `cache_with_state`, no
  test of a trainable start state, or no recipe in the docs fails this ticket.

**Current behaviour:**

- `has_learnable_init_state` of `Mamba2Config` and `Mamba3Config` builds
  `init_state_hpr: Option<Param<Tensor<3>>>`, of shape
  `[nheads, per_head_dim, state_rank]`, at zeros.
- Each forward gives it to the SSD input bundle. `Minimal` adds it, broadcast over the
  rows, to the start state of the call. `Serial` and `SerialRecalculated` panic.
- `step` does not read it. A forward from a cache that a call returned adds it again.
  A packed call with it panics.
- `Mamba2Untied::InitState` and `Mamba3Untied::InitState` untie it. The block
  contracts leave `InitState` out. The untied table tests list it.
- `forward_packed(x, cache, origin, …)` of each family already takes a start state
  from the caller. The **Triage notes** give the tests that cover it.

**Desired behaviour:**

- The block holds no initial state. These items go:
  - `init_state_hpr` of `Mamba2` and `Mamba3`, and `has_learnable_init_state` of their
    configs.
  - `InitState` of `Mamba2Untied` and of `Mamba3Untied`.
  - The `init_state_hpr` field of `Mamba2SsdInput`, `Mamba3DoubleSsdInput` and
    `Mamba3SingleSsdInput`, and its use in the 9 scans.
  - The 6 panics of the serial scans that refuse it.
- A caller gives `h₀` in a cache:
  - In `cache`, for the start of each row of a call.
  - In `origin`, for the start of each segment of a packed call. Each segment of a
    packed row then gives what it gives as its own row, from `h₀`.
- The tensor decides whether `h₀` trains. A trainable tensor gets a gradient on every
  SSD path. A constant tensor gives a fixed start. A call with no cache starts from the
  zero cache, as today.
- No call adds `h₀` to a cache. So a forward over two windows equals one forward, and
  `step` unrolled equals the forward, from any start cache.
- The zero cache stays all zeros, and it keeps its name.
- The `Block` adapters of Mamba-2, Mamba-3 and `MambaBlock` give the origin of
  `Block::block_forward_packed` (burn-stack ticket 18) to the family `forward_packed`.
  So a container can start each segment from `h₀`.
- A block with no initial state today gives the same values after this ticket.

**Key interfaces:**

- **`Mamba2::cache_with_state(&self, state_hpr: Tensor<3>, batch: usize) -> Mamba2Cache`**
  and **`Mamba3::cache_with_state(&self, state_hpr: Tensor<3>, batch: usize) -> Mamba3Cache`**:
  - The zero cache of `batch` rows, with `ssm_bhpr` equal to `state_hpr` broadcast over
    the rows.
  - Each other field is that of the zero cache. For Mamba-2, this is the conv window.
    For Mamba-3, these are the tap FIFO, the rotation and the registers of the positive
    systems.
  - It keeps the graph of `state_hpr`, so a gradient reaches it. It uses the device of
    `state_hpr`.
  - It asserts the shape `[nheads, per_head_dim, state_rank]`.
  - Its doc gives the recipe. The caller holds `h₀` as a `Param` of its own module,
    calls `cache_with_state`, and gives the result as `cache`, as `origin`, or as both.
    The doc says that the tensor decides whether `h₀` trains.
  - The recipe also gives these rules of Burn. Each one cites
    `../burn-stack/docs/burn/autodiff-semantics.md`:
    - Hold `h₀` as a `Param<Tensor<3>>`, not as a plain `Tensor` field. A plain field
      is a constant: no mapper, optimizer or record sees it (§9.3, trap 4).
    - In training, build the cache from `h0.val()` in each step. Burn runs one
      backward for each graph (rule 7, trap 11).
    - For a decode or an evaluation, use a plain device or `model.valid()`. If not,
      each step depends on a trainable leaf, and the graph grows with no limit
      (rule 6, trap 13).
    - A constant start is a plain tensor, or `x.without_autodiff()` (§10, "A constant
      inside a tracked op"). A plain input of an op acts as a constant (rule 2).
    - A trainable `h₀` has the checkpointing strategy of the block. If not, the first
      op that mixes them panics (rule 2, trap 2). A `Param` of the same model module
      gets the same `train`, `valid` and `fork` as the block.
  - It builds the other fields on `state_hpr.device()`. That device reports the
    autodiff context of `state_hpr`, so the new fields take that context (rule 1,
    §2).
- **The `Block` adapters**: `block_forward_packed` gives its origin as `Some(origin)` to
  the family `forward_packed`. `MambaBlock` gives each family the origin of its own
  cache type.
- **The docs**:
  - `GLOSSARY.md`, **Learnable initial state**: rewrite the entry. Do not delete it.
    The new text: "A state `h₀` that the caller trains. The caller gives it as the state
    of a cache. The cache of a call gives the start of each row. The origin gives the
    start of each segment. The block holds no parameter for it. Every SSD path of
    Mamba-2 and Mamba-3 takes it." Keep `_Avoid_: origin`.
  - `GLOSSARY.md`, **Origin**: delete the entry. burn-stack ticket 18 moves it to the
    glossary of burn-stack.
  - A new ADR, `docs/adr/0011-…`: the learnable initial state is a cache that the
    caller gives. It states three options:
    - A block parameter that each forward adds.
    - A block parameter in the zero cache.
    - A cache from the caller: the decision.

    Its consequences:
    - The caller owns the tensor, its trainability and its optimizer settings. The
      official code sets no weight decay on `init_states`.
    - The rules of Burn for a trainable tensor apply to `h₀`. The ADR cites
      `../burn-stack/docs/burn/autodiff-semantics.md`, and it does not repeat it.
    - Every SSD path, `step`, a split into windows and packed rows give `h₀` one
      meaning.
    - Each packed segment starts from the origin. The official code starts only the
      first sequence of a packed row from `init_states`.
    - A record that holds `init_state_hpr` does not load. There is no migration.
  - `docs/source-terms.md`, the row of `init_states`: our term stays **Learnable
    initial state**. Its wrong port: "A port can make it a parameter of the block, or
    add it at each call."
  - Each doc and comment that names `init_state_hpr` or `has_learnable_init_state`, or
    says that only `Minimal` supports the initial state. Some examples:
    - The doc of `SsdPath`.
    - The doc of the zero cache of Mamba-2, and the doc of `Mamba2::step`.
    - The module header of `family`.
    - The comments in the standard scan and in the serial scans.
    - The doc of the block contract settings.
  - ADR-0009 does not change.

## Comments

### After burn-stack ticket 12 and ticket 23

> *This was generated by AI during the triage of burn-stack ticket 12.*

The maintainer accepted burn-stack ticket 12
(`../burn-stack/.scratch/arch-review-backlog/issues/12-one-cache-stack.md`) and its
burn-mamba half, ticket 23. This ticket waits for ticket 23. After both:

- A block always gets a cache. `block_forward`, `block_forward_packed` and
  `block_step` take `Self::Cache`, and a container starts each slot from
  `zero_cache`. So the zero cache is the only start of a block in a container.
- The family API keeps its `Option`. A `None` there starts from `zero_cache`. So `h₀`
  in the zero cache also reaches a call with `None`.
- The block contract `zero_cache_equals_no_cache` is gone. So a zero cache that holds
  `h₀` breaks no contract.
- `zero_caches_for` did not change. It still builds each slot from application 0 of
  the first real layer. Decision 4 of burn-stack ticket 12 gives this ticket that
  change: build each slot from its own real layer and application. So an untied
  `InitState` gives each slot the copy of its application.
- That change also gives each slot of a hand-built mixed stack the zero cache of its
  own family. ADR-0009 says that such a stack panics at a `step` with no cache,
  because the first block sizes each zero cache. That consequence then changes.
