# 01: One plant frame around the three scans

Status: resolved

Blocked by: None

From the architecture review of 2026-11-03. Line numbers are those of commit
`42ca3d0e`. The review compiled nothing here.

**Files:** `src/mamba3/double_ssd/double_ssd/mod.rs:77-267,497-585,658-778,823-893`,
`src/mamba3/single_ssd/single_ssd/mod.rs:116-345,561-636`.

**Problem:** One plant option costs three edits: the double-SSD forward, the
single-SSD forward and `step`. A reader must diff 300 lines to find what a pathway
changes. Normalised, 114 of 126 pre-scan lines and 44 of 53 tail lines of double-SSD
occur in single-SSD. `step_project` and `step_finish` are a third copy, one rank
lower. The copies drift: `D:241-248` asserts the shapes of B and C, and single-SSD
does not.

**Direction:** One routine from `project_in` to the rotated B, C and masses. One
routine from the readout to `out_proj`. `step` enters at `tokens = 1`, as the
comments at `D:742-744` and `D:945-948` already describe. Each pathway keeps only
its middle.

**Decided with the user:**

- ADR-0007 is amended in this work. Independence covers the scans. The pre-scan
  work and the tail are one module with their own tests.
- The user runs `./bench.sh` before and after. Decode kernels are shape-sensitive
  (`helpers.rs:771-774`). If decode slows down, `step` keeps its own frame, and only
  the two forwards share one.

**Do this before `02-in-projection-layout.md`,** so that only one split remains to
convert.

**Trade-off:** A wrong split or gate then fails both sides alike, so parity cannot
see it. The frame needs its own tests.

### Agent brief

**Category:** enhancement

**Summary:** Move the work around each Mamba-3 scan into one `pub(crate)` module, the
plant frame. Both forward pathways and `step` call it. This brief replaces the
**Direction** above.

**Current behaviour:** `forward_double_ssd_packed` and `forward_single_ssd_packed`
hold the same work before and after their scans. `step_project` and `step_finish`
hold that work again, one rank lower. The copies drift:

- The double-SSD forward asserts the shapes of `B` and `C`. The single-SSD forward
  asserts neither, and `step_project` asserts only `B`.
- The single-SSD forward has no direct sanity check of `ν`.

**Desired behaviour:** The outputs, final caches and gradients of every pathway and
SSD path stay the same. Each pathway keeps only its middle.

**Key interfaces:** `src/mamba3/plant_frame.rs` holds two routines on `Mamba3`.

- **The entry** starts at the dimensions and assertions at the top of a forward. It
  holds the padding, the segments, the fresh cache, the origin, the in-projection,
  the split, the trapezoid coefficients, QK-Norm, the rotation and `save_tap_slots`.
  It returns one struct with one named field for each stream.
- **The tail** starts at `positive_tail`, after the readout. It holds the `D` skip,
  the gate, the MIMO merge and `out_proj`. The band correction of single-SSD runs
  before the tail and stays in that pathway.

**Constraints:**

- The frame uses one cache type, `Mamba3DoubleSsdCache`. A forward starts at a call
  boundary, so the existing `From` impls convert the single-SSD cache (ADR-0003).
- `step` has no SSD path. So the entry takes the chunk length only together with the
  resets.
- The entry keeps the checks of the double-SSD forward: the `B` and `C` shape
  assertions and the sanity check of `ν`.
- `λ` stays an `Option` in the entry. The delegation for `TapPattern::None` and the
  `expect` on `ν` stay in single-SSD.
- The fields of the struct move out to the code that uses them. Each tensor must drop
  no later than it does now. Do not hold the struct across the scan.
- Each scan stays independent (ADR-0007). `beta_side` and `tap_write` stay separate.
  The key scale, the boundary seed and the band stay in single-SSD.

**Order of work:** Make two commits.

1. Both forwards call the frame. `step` does not change.
2. `step` calls the frame with a read axis of length 1. It adds that axis to its
   input and removes it from its output. Delete `step_project`, `step_finish` and
   `StepProjection`.

**Benches:** The agent stops after commit 2, because only the user runs the benches.
The user runs `./bench.sh` and `./kernels.sh` before commit 1 and after commit 2.

- Commit 2 stays when each `step` case keeps its launch count, and its time stays
  within run noise as the user judges it.
- If commit 2 fails that condition, revert it. `step` then keeps its own frame, and
  only the two forwards share one.
- Commit 2 changes these forms in `step`: `in_proj` and `out_proj` get a read axis,
  the splits move to dim 2, and the gate runs at rank 5. The `D` skip changes from
  expand-then-multiply to a broadcast.
- The `helpers.rs:771-774` of the **Decided** section describes `mimo_outer_sum`.
  That function stays in the middle of `step`, with the same shapes. The same comment
  says that a broadcast can be more than 10× slower on the portable CPU backends. So
  look at the `D` skip first. No run measured this cost.

**Tests:** Parity cannot see a bug that both sides share. Expected values come from
the definitions, not from the code (`docs/agents/testing.md`). The new tests belong
to the seam "Mechanism against its direct form". Add
`src/mamba3/plant_frame/tests.rs` to that row.
