1//! # The unified, runtime-selectable API
2//!
3//! [`burn_stack`] composes any [`Block`](burn_stack::modules::Block) into
4//! layers and networks, but `M` is fixed at the type level. To let a caller
5//! choose the family at *runtime* — and to serialize that choice — this module
6//! wraps the three monomorphisations in enums: [`MambaLatentNet`] /
7//! [`MambaVocabNet`] / [`MambaBidiLayers`] / [`MambaCaches`] /
8//! [`MambaSsdPath`], each with a `#[derive(Config)]` companion where one
9//! applies. They panic on a family-mismatched cache or SSD path.
10//!
11//! This is also where the three families meet the generic stack: the
12//! `impl Block for Mamba{1,2,3}`, `impl BlockConfig for Mamba{1,2,3}Config` and
13//! `impl CacheStack for Mamba{1,2,3}Caches` blocks live in [`cache`].
14//!
15//! ## Muon: why the 3-D tensors are not "stacked matrices"
16//!
17//! [`burn_stack::optim`] only lets Muon own weights a
18//! [`BlockConfig::muon_projections`](burn_stack::modules::BlockConfig::muon_projections)
19//! names, and each family's list deliberately stops at rank 2. For Mamba-3's
20//! MIMO tensors that deserves an argument, since their *shape* invites the
21//! opposite conclusion:
22//!
23//! MIMO's *math* is R independent SSMs summed together, so a `[nheads,
24//! mimo_rank, per_head_dim]` tensor looks like a stack of matrices that a
25//! stack-aware Muon could take a slice at a time. It is not: the paper
26//! deliberately avoids instantiating the R maps, because that would multiply
27//! every per-head projection's parameter count by R (`DP → DPR` *per head*).
28//! Instead it keeps the SISO projection and element-wise scales its output to
29//! size R with a learnable vector (`DP + PR` per head) — in the appendix's
30//! contraction notation `X = contract(PR, P → PR)(W_X, X')`, where `P` appears
31//! in both inputs *and* the output and so is never contracted. `mimo_x`/`mimo_z`
32//! /`mimo_o` are therefore **diagonals**, and their matrix shape is a layout
33//! coincidence; orthogonalising one would constrain a set of gains. The part of
34//! MIMO that really is an R-fold matrix expansion is B/C (`DN → DNR`), which
35//! lives in `in_proj` and is already Muon's. The remaining 3-D tensors are a
36//! bias (`b_bias_hmr`/`c_bias_hmr`), an initial condition (`init_state_hpr`), or
37//! a depthwise filter (the Mamba-1/2 conv) — diagonal or embedding-like again.
38//!

59/// An explicit, family-tagged SSD-path selector for the unified API.
60///
61/// Each variant carries the concrete per-family path so callers can choose the
62/// algorithm/chunk explicitly; the `*_default` constructors offer the common
63/// "ride along the family default" path without making it the *only* option.
64#[derive(Debug, Clone)]
65pub enum MambaSsdPath {
66    /// Mamba-1 has no SSD chunking (path is the unit type).
67    #[cfg(feature = "mamba1")]
68    Mamba1,
69    /// Mamba-2 SSD path.
70    #[cfg(feature = "mamba2")]
71    Mamba2(crate::mamba2::prelude::Mamba2SsdPath),
72    /// Mamba-3 SSD path.
73    #[cfg(feature = "mamba3")]
74    Mamba3(crate::mamba3::prelude::Mamba3SsdPath),
75}
76
77impl MambaSsdPath {
78    /// The Mamba-2 default path (`SerialRecalculated`, optimal chunk).
79    #[cfg(feature = "mamba2")]
80    pub fn mamba2_default() -> Self {
81        Self::Mamba2(Default::default())
82    }
83    /// The Mamba-3 default path (`SerialRecalculated`, optimal chunk).
84    #[cfg(feature = "mamba3")]
85    pub fn mamba3_default() -> Self {
86        Self::Mamba3(Default::default())
87    }
88}
